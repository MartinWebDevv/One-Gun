# One Gun — Architecture

> Godot 4.7.1, Forward+ rendering, Jolt physics. Terrain3D 1.0.2 is retained in `addons/` for reference but its incompatible native extension and editor plugin are disabled because no current game scene uses Terrain3D. Git is initialized. There are still several stray Godot autosave `.tmp` files in the project root (`game_setup.tscn*.tmp`, `node_3d.tscn*.tmp`) from unsaved/crashed editor sessions — worth cleaning up (see [TODO.md](TODO.md)).

## 1. Autoloads (Singletons)

Registered in `project.godot` under `[autoload]`, load order as listed:

| Singleton | Script | Responsibility |
|---|---|---|
| `GameEvents` | `game_events.gd` | Global signal bus — the only cross-system coupling mechanism for match events |
| `GameConfig` | `game_config.gd` | All match-rule state (teams, melee lethality, dash charges, item toggles, bot configs) + disk-backed preset save/load (`user://match_preset_slots.json`, 5 slots) |
| `PlayerPrefs` | `player_prefs.gd` | Personal settings (volume, sensitivity, FOV, crosshair color, sprint toggle mode) — disk-backed (`user://player_prefs.json`), always-on autosave, distinct from `GameConfig`'s shared "house rules" |
| `PauseManager` | `pause_manager.gd` | Owns ESC key routing (`PROCESS_MODE_ALWAYS`) so nested overlays can claim `escape_override` instead of every screen handling ESC independently |
| `MeleeWeaponRegistry` | `melee_weapon_registry.gd` | Defines the 5 `WeaponData` resources (Sword/Bat/Stick/Crowbar/Frying Pan) and tier/effect randomization logic |
| `ThemeManager` | `theme_manager.gd` | Builds and applies the shared `Theme` resource at startup (saves to `res://one_gun_theme.tres`) |
| `AudioManager` | `audio_manager.gd` | Music/SFX playback, bus volume control, `PROCESS_MODE_ALWAYS` |

## 2. Scene Flow

```
main_menu.tscn  →  game_setup.tscn (lobby)  →  <selected map>.tscn (match)  →  back to main_menu.tscn
                                                        │
                                          RoundManager (per-map Node) drives
                                          round/set/match state for that scene
```

- Maps live under `maps/test/` (`NewMap.tscn`, `NukeTownMap.tscn`) plus a root-level `node_3d.tscn` (Coliseum-style arena) and `title_bg_map.tscn` (used only as the main menu's live 3D background).
- Each map scene contains its own `RoundManager` node instance (`round_manager.gd`), spawn-point markers (`spawn_point` group), and a `gun_spawn_point` group for `"random"` gun spawn mode.
- Player instances come from `player.tscn`; bots are spawned at runtime from `DummyModel.tscn` (`dummy.gd`) by `RoundManager._spawn_bots()`.
- Online lobbies can branch into `maps/playpen/playpen.tscn` before launching a match. `playpen_manager.gd` subclasses `RoundManager` only to reuse actor/item/melee RPC contracts; it suppresses round scoring/timers, creates the procedural retro-space arena, manages infinite respawns, and owns three deterministic armory bays. Guests may return to `game_setup.tscn` without ending the practice session; the network host owns the authoritative room and closing it returns every remaining member to the lobby.

## 3. Player Architecture

`character_body_3d.gd` (attached to `player.tscn`, a `CharacterBody3D`) is the single script driving both P1 and P2 in splitscreen — differentiated entirely by the exported `input_prefix` (`"p1"` / `"p2"`) and `use_gamepad_look` flag, rather than by separate scripts or scenes. This is the key pattern for the whole input layer: every `Input.is_action_*` call is built as `input_prefix + "_action_name"`, so splitscreen support is a matter of instancing the same scene twice with different prefixes, not maintaining parallel code paths.

Bots (`dummy.gd`) are a **separate script** from the human controller, not a subclass or a shared-base-class specialization — they reimplement movement/combat decisions independently, driven by a difficulty-tuned decision loop (`_decide_objective`) instead of input polling. This means gameplay-affecting tuning (speed, stamina, dash) that lives as `const` in `character_body_3d.gd` must be mirrored by hand in `dummy.gd` if it needs to match; there's no shared base class enforcing parity.

Bot pathfinding uses the `NavigationAgent3D` in `DummyModel.tscn` and one baked `NavigationRegion3D` per gameplay map. City, Forest, and Western keep their baked polygon data in `navigation/*MapNavigation.tres` so scene edits cannot silently leave an empty inline `NavigationMesh`; `tools/bake_existing_navigation.gd` rebuilds those resources directly from each map's static colliders. NukeTown retains its inline bake. All maps expose player/bot starts through the shared `spawn_point` group. `dummy.gd` applies a 1.0 m `path_height_offset` so floor-height path points align with the bot body's movement plane and reached waypoints advance correctly.

Reusable City building variants `models/cityAssets/BuildingC_Enterable.tscn` and `BuildingB_Enterable.tscn` wrap the original GLBs without replacing them. Each has permanent front and right-side openings, one open playable ground floor, solid transparent window colliders, full upper-shell/roof collision, and navigation entry markers. No current City-map instance references either variant until an authored placement is chosen and the City navigation resource is rebaked.

Key subsystems inside `character_body_3d.gd`:
- Movement/physics (`_physics_process`): walk/jump/dash plus sprint/stamina code. The match-wide `GameConfig.sprinting_enabled` setting gates sprint for both humans and bots and defaults off. Human jump impulse is exported as `jump_velocity`; there is no post-landing timer gate, so the raw grounded state is the only normal re-jump requirement. The separate 0.12s terrain-floor grace affects animation selection only. A manhole launch establishes a separate steam-flight state on human and bot controllers. Spring pads use a different state: 13.0 vertical launch, a first-input 1s window for a committed 4.0 horizontal boost, and a 60% blend toward normal air steering until landing. Maple & 3rd's `HydrantWaterPush` tests actor positions against the map-authored nozzle-side `CollisionShape3D`, waits for ordinary upward jump velocity, then applies a 15.0 m/s impulse toward a separate `LaunchDirection` marker. Human and bot controllers decompose their existing horizontal velocity into with-stream and cross-stream components: perpendicular and with-stream motion survives, while opposing motion retains 25% before the impulse is added. A water-specific airborne floor then preserves at least 40% of the impulse's horizontal stream speed against opposing air input without touching the perpendicular component. Vertical velocity uses the greater of the current rise and the water arc, avoiding jump-force stacking. Separating trigger geometry from launch direction preserves level-editor collision adjustments and prevents the particle emitter's visual rotation from creating sideways gameplay force. The water launch otherwise uses the same steerable air state. An airborne dash explicitly clears either pad or water momentum before applying the dash, preventing launch force from stacking with dash force. The host sends all launch contracts to online actors; decoys implement the non-dash spring contract as well.
- Weapon/item slot management: `active_slot` state (`"none"` / `"weapon"` / `"item1"` / `"item2"`), `get_hold_point()` / `get_melee_hold_point()` / `get_item_hold_point()` node lookups for attaching held objects. Rendered players resolve the animated sockets under `CharacterModel`; dedicated-server players lazily create invisible gameplay-only `Marker3D` sockets under `AimPivot`, ensuring authoritative held objects remain in the active SceneTree even when presentation nodes are unavailable. Pickup code validates the target socket before detaching an object from the world, so a missing socket cannot orphan the gun, melee weapon, or item. See §6 for the full pickup/swap/hold-drop architecture.
- `nearby_interactables`: normally populated by pickup Area3Ds registering themselves (`register_interactable`). Reach adds a throttled 8m, line-of-sight scan of gun/melee/item/powerup groups and merges those candidates into the same array; powerups collect on contact with that scan while other pickups still require Interact. Host pickup validation uses the same `GameConfig.REACH_POWERUP_DISTANCE`. During a Reach swing, each physical melee shape is extended and shifted outward so its near end remains at the holder and its far end reaches 8m; local and host hit resolution both enforce that same 8m maximum instead of the shorter normal 5.5m cap.
- Status effects: knockback, stagger, slow, flash blindness, bullet immunity, disarm-shield, and Reach — implemented as timers/flags on the controller itself and mirrored explicitly in `dummy.gd` where bot parity matters.
- Human visual/animation runtime: `player.tscn` instances `models/player_v2/player_v2_visual.tscn`, which uses `animations/Idle.fbx` as the single runtime mesh/skeleton master. The Blender-round-tripped `OGCatModelV2_Rigged.glb` remains the authored reference asset, but its Armature and skin-bind coordinate space is not directly compatible with the Mixamo FBX tracks. `player_v2_visual.gd` therefore bakes each named `animations/*.fbx` clip at 30 fps as a deformation relative to that clip's source bind/rest pose, reconstructs it against the Idle master's bind/rest pose, preserves authored vertical Hips motion, and removes only horizontal Hips travel so `CharacterBody3D` remains authoritative. The 4.87s Mixamo Throw Object take contains pickup, throw, and recovery actions; runtime deliberately slices source seconds 2.75–3.60 so the 0.85s action plays the actual throw rather than the opening toe-touch/pickup motion. Gameplay players preload the full named set once into a shared static cache; menu/showcase previews request Idle only, while decoys request Idle + Standard Run. Jump, melee, throw, and hit clips are one-shots; locomotion, falling, idles, and dances loop. Temporary `idle_pistol -> idle` fallback remains until dedicated pistol Idle/Fire/Reload clips arrive.
- `player_v2_visual.gd` also publishes scale-normalized top-level left/right sole sockets sampled between the animated Mixamo foot and toe bones while retaining character-facing axes. The split_spring_shoes tool separates the authored pair at its Z=0 center plane into two complete recentered GLBs; the wearable scenes orient one full shoe per paw and keep both spring coils vertical beneath the sole. Equipment follows those sockets without inheriting the imported rig's oversized skeleton scale or moving the gameplay camera.
- Human skin/material runtime: `player_skin_registry.gd` is the stable ID/display-name/texture/portrait registry for all 13 variants. `PlayerV2Visual.set_skin()` creates and rebinds authoritative per-instance material overrides, so changing one local/online player never recolors another and temporary effects cannot strand the mesh on a textureless material. The shared `CharacterCustomizationOverlay` uses one isolated rotating 3D preview plus a 5/5/3 grid of static right-facing portraits generated from that same model by `tools/generate_character_portraits.gd`; this avoids thirteen live preview viewports. P1/P2 maintain independent pending selections, and Back/Escape discards them while Confirm commits them to `PlayerPrefs`, session-only `GameConfig.player2_skin_id`, or `NetworkManager` as appropriate. Online peers synchronize only the stable skin ID and resolve the matching portrait locally, so every roster sees the same lightweight image without transferring image data. `CharacterPortrait` also supplies the main-menu profile card and human lobby rows. Runtime right-hand sockets follow `mixamorig_RightHand` position each frame, while their axes stay aligned with the character-facing basis used by the original weapon transforms; this prevents Mixamo wrist roll from turning guns/melee sideways without embedding objects in every FBX. During `idle_pistol`, the gun socket blends downward to the relaxed paw and pitches 55 degrees toward the ground; both adjustments blend back to the normal placement for movement and airborne pistol animations. Hit flashes duplicate the selected textured material, use generation-safe restoration, and explicitly rebind the current skin after overlapping flashes. Victory presentation hides the held gun for the complete dance and resets that presentation state on respawn.

- Gun-holder and reveal presentation: other players see a line-of-sight-gated `GUN HOLDER` billboard plus a pulsing depth-tested Fresnel rim applied only to bound character skin meshes. Overtime and the 0.5s decoy-destroyer reveal use a through-cover variant of that same real-surface rim. None of these paths expands an inverted hull, so the heavily scaled V2 import cannot become a solid shell and held equipment is unaffected. Temporary reveals explicitly clear their overlay before restoring any applicable gun-holder rim; this matters in local play, where the gun holder intentionally has no shared mesh rim. The holder never sees their own gun-holder marker.

## 4. Weapons Architecture

- `weapon_data.gd` — a `Resource` subclass holding a melee weapon's static stats (reach, windup/active/recovery base times, stamina cost, raw model length, model-local grip anchor, held orientation/scale, and model path). `melee_weapon_registry.gd` constructs one `WeaponData` instance per weapon type at `_ready()` and hands out random picks. It divides the shared 1m held-length target by each measured raw model length, preventing differently authored source units from making one weapon appear tiny. Each grip anchor maps the imported handle base to the V2 paw socket. Normal custom hitboxes inherit the same root rotation, anchor, and normalized visual scale before their width allowance is applied, then extend outward from the paw using tier-driven linear interpolation: T1 is 3.0m, T2 is 3.4m, and every T3 weapon shares the 3.8m maximum. The character's authored melee animation supplies all visible swing motion; the weapon's physics-phase sequence only opens/closes the hit window and handles recovery.
- `melee_weapon.gd` (on `melee_weapon.tscn`) is the generic scene used for every weapon/tier/effect combination the registry rolls — the model, stats, and effect are applied onto each instance rather than requiring 5 separate weapon scenes. `MeleeWeaponRegistry.get_random_weapon_data()` filters through `GameConfig.melee_weapon_registry`; config normalization and the lobby both guarantee at least one enabled type. `RoundManager` populates every authored melee marker at round start and schedules that marker's fresh randomized instance 5s after its weapon is picked up. On OT transition, held melee is preserved, regular placements are retired, and one selected OT supply marker continues the same refill contract.
- `gun.gd` (on `gun.tscn`) is a `RigidBody3D`: physics-frozen and parented to the holder's hold point while held; explicitly unfrozen **and awakened** when dropped on swap/death/disarm so gravity carries it into world geometry; `reset_to_spawn()` each round. Online drops synchronize the release position, then every peer simulates the same gravity-driven fall instead of freezing the gun in mid-air.
- `bullet.gd` (on `bullet.tscn`) is fire-and-forget: instantiated by `gun.fire()`, travels at a fixed speed, checks `GameConfig.can_affect()` (teams/friendly-fire) and target bullet-immunity, then eliminates and frees itself on contact. Human shots start on the camera viewport's exact center ray at the physical muzzle's forward depth, keeping the projectile aligned with the procedural crosshair despite the third-person shoulder/muzzle offset; camera-less bot shots still originate at the physical muzzle and use their configured aim/spread.

## 5. Items & Powerups Architecture

- `item.gd` (`item.tscn`, `grenade.tscn`) — generic held/throwable consumable container, data-driven via `item_type` + `deployed_scene`. Fire press/release is split into `begin_use()` / `release_use()` so all ordinary throwables can preview while held and commit on release. Grenades specialize this path: `fuse_time` starts at Fire press, the use becomes non-cancellable, remaining fuse is preserved through the authoritative throw, and expiry can deploy directly from the holder's hand. Other positive-fuse items still begin their fuse after release. Marker-authored items claim their independent 8s randomized refill when picked up; the carried instance retires after use, preventing a duplicate refill.
- `bubble_gum_trap.gd` (`bubble_gum_trap.tscn`) — the deployed hazard instance spawned when a thrown item lands; owns its own **lingering** Area3D slow effect and respawn timer, independent of the item pickup itself. Stays live until players walk into it or its lifetime expires.
- `grenade_explosion.gd` (`grenade_explosion.tscn`) — a **one-shot** 7.5m query, not a lingering hazard. On `_ready()` it applies team-aware knockback with linear 4.0→2.0 center-to-edge falloff, including self-effects, then frees itself. Online uses the same falloff through `RoundManager`.
- `smoke_cloud.gd` (`smoke_cloud.tscn`) — a 5m-radius, 4.2m-half-height ellipsoidal concealment volume rather than the former sphere. Presentation uses overlapping camera-facing procedural smoke masks: alpha-scissored inner wisps prevent scenery bleed-through, while densely layered moving outer wisps restore a soft, irregular silhouette. It changes bot/visibility line-of-sight but has no collider, so bullets continue through it.
- `decoy_body.gd` (`decoy_body.tscn`) — a self-contained `CharacterBody3D` combat target with a 10s authoritative lifetime. Default movement runs straight forward; pressing C toggles owner-direction mirroring. Only the physics authority moves the body, while remote peers interpolate toward received transforms without extrapolation. Its visual is the shared V2 human rig, copies the owner's selected skin, and switches between in-place Idle/Standard Run clips; the procedural gait remains only as an import-failure fallback. The decoy keeps the existing combat-target, team-protection, bot-targeting, trap/status, shooter-reveal, identity-tag, and synchronized online action contracts without joining the real `player` group.
- `double_jump_shoes_item.gd` (`double_jump_shoes.tscn`) — a use-in-place `item.gd` specialization. Activation consumes the carried instance and attaches the split left/right shoe scenes to the actor feet on every peer. The controller holds one boolean charge; an accepted mid-air Jump applies 50% of normal jump velocity, plays the boing SFX, removes both attachments, and is host-confirmed online. A player may carry another pair while one charge is active, but cannot activate the second until the first is spent.
- `flash_camera.gd` (`flash_camera.tscn`) — an `item.gd` specialization with no throw path. Its first Fire enters a framed local camera overlay and its second requests a photo. Local/host validation shares the 30m range, 60° view/facing cones, viewport frame, line-of-sight and `GameConfig.can_affect()` checks; accepted targets receive a distance-scaled 6s→3s flash whose first 2s are opaque white before a linear fade over the remaining duration. The viewport-scoped overlay safely supports human, bot, and followed-spectator HUD targets. The shipped mesh is procedural placeholder art so a final model can replace the scene visuals without changing gameplay.
- `powerup.gd` (`powerup.tscn`) — marker-spawned pickup with a fixed type until collection. A billboarded `Label3D` displays the resolved player-facing name above the orb and updates alongside its type color on local or synchronized online respawn. Contact applies the effect to the player (`apply_powerup()` on the controller), then the marker re-rolls and respawns after 8s. Both local rolls and host-authored online assignments use `GameConfig.enabled_powerup_types()`; an empty pool produces no placements.
- `powerup_status.gd` — pure UI, listens for active powerup state on the local player to render the countdown stack; not itself a gameplay system.
- **Throw arc**: `item.gd` and `melee_weapon.gd` expose the actual launch origin/velocity/gravity to `throw_arc_overlay.gd`. The overlay simulates only a short dotted portion, stops at the first physics collision, and intentionally has no landing marker. It binds to the local actor or current follow-spectator target. Release uses the same data, keeping the preview honest; Flash Camera overrides the interface to disable it.

## 6. Pickup / Interact / Swap Architecture

The interact button drives all pickup, swap, and voluntary-drop behavior through one per-frame decision in `character_body_3d.gd._physics_process()` — see `docs/GAME_RULES.md` §9 for the player-facing behavior this implements.

- **`pick_up()` returns a `bool` now, on every pickup-able object** (`gun.gd`, `melee_weapon.gd`, `item.gd`) — `true` if the pickup/swap happened, `false` if it refused. This is the core contract: `character_body_3d.gd._try_interact()` just loops `nearby_interactables` calling `pick_up(self)` until one succeeds; it does not pre-compute eligibility (empty slot? valid swap? gun exception?) — each object decides for itself and reports back. Any future pickup type should follow this contract rather than having the player special-case it.
- **Tap vs. hold** is resolved once, at press time: if `_try_interact()` returns `false` (nothing nearby could be picked up/swapped), the press starts a hold timer (`interact_hold_active` + `interact_hold_timer`, threshold `INTERACT_HOLD_DROP_TIME` = 0.5s); crossing the threshold while still held fires `_drop_active_slot()` once. If `_try_interact()` succeeds, no hold timer starts at all — holding the button afterward does nothing.
- **Swap-in-place**: when an object's `pick_up()` needs to bump something the player already holds (melee-for-melee, melee-for-gun, item-for-item), it captures its own `global_position` before anything moves, calls `.drop()` on the old object, then repositions the old object to that captured spot. This is what makes the displaced item land exactly where the new one was instead of at the player's feet.
- **The gun exception is enforced in `melee_weapon.gd`, not the player**: `pick_up()` returns `false` immediately if `p.holding_gun` is true, with no auto-drop. Putting this at the object level (rather than only gating it in the player's input code) means it can't be bypassed by another caller — bots included, even though they call `pick_up()` directly with no tap/hold concept at all.
- **Item slots are dual, weapon slot stays singular**: `character_body_3d.gd` exposes `held_item_1`/`held_item_2` plus a small interface — `can_pick_up_item()`, `assign_item()`, `clear_item_slot()`, `get_active_item()` — that `item.gd` calls generically instead of touching slot fields directly. `dummy.gd` (bots) implements the same method names against its own single `held_item` field, so `item.gd` has one code path for both: `if p.has_method("can_pick_up_item"): ... elif "held_item" in p: ...`.
- **Bots bypass the tap/hold system by design, not oversight**: `dummy.gd` keeps a simpler single-`held_item` model and calls `pick_up()` directly — every bot pickup is effectively an instant tap. The gun exception above still protects bots as a free side effect, and bots additionally already gate their own melee-pickup attempts on `not holding_gun` before ever calling `pick_up()`.
- **Both item slots share one physical attachment point**: there's no second `ItemHoldPoint` node on the character model, so `held_item_1` and `held_item_2` both parent under the same node when held. `_update_active_slot_and_visuals()` toggles each held item's `.visible` individually based on which slot is active, so only one item is ever rendered in-hand even though both are legitimately held.

## 7. Round/Match State Machine (`round_manager.gd`)

The state path is `"countdown" -> "live" -> "overtime" -> "ended"` when the adjustable round timer expires with multiple survivors; otherwise live play proceeds directly to ended as before. The timer accepts whole-second values from 1–900, while 0 keeps the unlimited option. OT boundaries are centered on the midpoint of authored gameplay markers rather than assuming the gun spawn is the map center. Future maps can override the inferred footprint with `overtime_boundary_point` markers and the inferred midpoint with one `overtime_center_point`. The axis-aligned X/Z extents are shared by damage and visuals, and damage deliberately ignores Y so elevated players above unsafe floor remain exposed. The visual fire is generated from the first non-empty baked `NavigationRegion3D`; if a bake is absent, `round_manager.gd` emits a warning and builds an emergency projected-floor surface rather than leaving lethal ground invisible. Survivor reveal pulses use a depth-free Fresnel rim on character skin meshes only, so the V2 model remains recognizable through cover without expanding into a scale-dependent solid shell or including held props.

The manager owns a 5s opening approach followed by an uninterrupted inward close that fully engulfs the arena at about 2:00. At OT start, it copies the map's baked `NavigationMesh` polygons into a slightly raised visual-only mesh. A world-space shader reveals only the unsafe portion of that continuous playable surface, independent of whether the underlying imported mesh, CSG or Terrain3D material accepts decals. Deduplicated navigation vertices and triangle centroids feed one high-rate, short-lived `CPUParticles3D` emitter, adding fast-rising vertical flames at the same active boundary. Valid unsafe-floor points are assigned before the emitter starts so it cannot create a fallback particle at the arena origin. A 0.35-unit visual lead guarantees the floor becomes visibly dangerous before exposure begins. Because a baked navigation region is already mandatory for game-ready maps, future maps automatically use this path. The same manager owns exposure counters, zone pulses, Standard/Chaos gun rules, and millisecond-resolution tiebreak data.

- Dispatches mode-specific round setup from `GameConfig.game_mode`. All Gun replaces the shared gun with personal guns plus synchronized three-heart state rendered both in HUD and as depth-tested filled/empty Label3D markers above every actor, removes ground melee, filters Extra Life from its spawn pool, converts disarms to reloads, and makes OT fire immediate sudden death. One of Us asks each human for a session-only private volunteer preference, lets the host choose randomly from that private pool (or all participants when empty), synchronizes the resulting host-selected role dictionary before loadout/reset, grants Us three base dashes plus personal guns and Them four base dashes plus personal Tier 3 swords, owns 1.5s conversion and 2.0s infected respawn generations, filters temporary spectator targets by role, awards the final Us one fourth single-use dash, and resolves the fixed 180s role win condition as a winner-takes-all match without sets or OT. Its bot target policy always seeks the nearest opposing role, with Them hunting into melee range and Us retreating toward gun spacing while maintaining line-of-sight fire. A duplicated runtime Environment supplies the darker/desaturated/cool-fog grade only for this mode, leaving authored map resources untouched.
- `one_of_us_intro.gd` is the modular 7.35s hunt cinematic layer: camera route stages, target-scan count, timings, text, FOV, glitch strength, and optional audio cue are tunable constants in one script. It builds a temporary camera above the arena, deterministically scans actors, dives behind the host-selected first infected, triggers their synchronized transformation, and runs a tightening unstable orbit. Role-specific endings either push through the infected into their body-look gameplay view or throw a survivor camera backward and sweep it to the local shoulder before transitioning home. `character_body_3d.gd` supplies the camera handoff and retains an input lock through the shared deadline; `one_of_us_role_visual.gd` supplies the non-blob infected rings, particles, and light pulse. The ordinary map intro path is unchanged for other modes.
Owns a single `round_state` string machine: `"countdown" → "live" → "overtime" → "ended"` (repeating per round), plus `round_number`/`set_number` counters and per-player dictionaries (`round_wins`, `match_points`, `stat_kills`, `stat_deaths`, `stat_disarms`, `stat_pickups`, `stat_melee`). It:
- Runs the first-round-only 3s introduction before countdown, reading one optional `round_intro_camera_point` from the active map and asking each human actor to orbit from it toward that actor's spawn. Actors remain frozen; Reduced Motion takes the fade-only branch.
- Spawns bots at `_ready()` from `GameConfig.bot_configs`.
- Filters players to those relevant to the current mode (drops P2 if splitscreen is off).
- Subscribes to `GameEvents` (`player_eliminated`, `player_disarmed`, `gun_picked_up`, `melee_hit_landed`) to update stats — **this is the only consumer of most of these signals for scoring purposes**; UI systems (kill feed, HUD) subscribe to the same signals independently for presentation.
- Computes scoreboard data on demand (`get_scoreboard_data()`), sorted by sets then rounds.
- Drives round/set/match end transitions and countdown timing, using the `@export` timing vars as the single source of truth for banner durations.

## 8. Global Event Bus (`game_events.gd`)

A minimal autoload with no listener/emitter registration logic — pure pub/sub. Actor-keyed signals are authoritative for scoring and combat feedback; legacy name-keyed signals remain for presentation-only consumers:

| Signal | Emitted by | Consumed by |
|---|---|---|
| `actor_eliminated(victim_actor_id, killer_actor_id, weapon_icon)` | validated bullet/melee/elimination paths | `round_manager.gd` (stats) |
| `actor_disarmed(victim_actor_id, disarmer_actor_id, weapon_icon)` | validated disarm paths | `round_manager.gd` (stats) |
| `actor_gun_picked_up(actor_id)` | `gun.gd` | `round_manager.gd` (stats) |
| `actor_melee_hit_landed(actor_id)` | `melee_weapon.gd` | `round_manager.gd` (stats) |
| `actor_combat_feedback(attacker_actor_id, event_kind)` | validated combat paths | `hit_marker.gd` |
| `player_eliminated(...)`, `player_disarmed(...)`, `gun_picked_up(...)` | gameplay presentation paths | kill feed / match HUD only |
| `gun_dropped()` | `gun.gd` | `match_hud.gd` (notification) |
| `hud_notification(message)` | `round_manager.gd` and other systems as needed | `match_hud.gd` |
| `combat_noise(world_position, source_actor_id, kind, loudness)` | footsteps/weapons/items | bot perception |

This bus is the primary decoupling mechanism in the codebase: gameplay scripts never hold direct references to UI or the round manager, they only emit signals and let interested systems subscribe.

## 9. UI Architecture

UI is composed of small, single-responsibility scripts, each polling or listening to one thing and rendering it, rather than one large HUD controller:

- `match_hud.gd` — round/set banner, remaining-player drama states, scoreboard overlay (TAB), notification toasts (via `hud_notification`).
- `gun_ui.gd` / `melee_ui.gd` / `reload_spinner.gd` — weapon/item status. The spinner renders both gun reload and grenade-cook progress with no numbers.
- `inventory_slots.gd` — the three-slot (weapon, item1, item2) display, including a per-slot `HoldBar` (`ProgressBar`) that fills while that slot's `interact_hold_active`/`interact_hold_timer` hold-to-drop is in progress (see §6).
- `item_ui.gd` — shows whichever item slot is currently active (mirrors how `gun_ui.gd`/`melee_ui.gd` only show while the weapon slot is active), not both items at once.
- `stamina_bar.gd` / `dash_charges.gd` / `powerup_status.gd` — player-resource displays, each reading directly off the local player controller.
- `throw_arc_overlay.gd` / `flash_camera_overlay.gd` / `flash_blind_overlay.gd` — viewport-scoped aiming/flash presentation. Keeping all three inside each HUD is essential in splitscreen: one player's arc, camera frame, or blindness must never spill into the other half.
- `crosshair.gd` / `UI/crosshair_renderer.gd` — one procedural renderer shared by local and online HUDs. It may visualize movement, firing, normalized `gun.get_reload_progress()`, and a camera-ray-validated nearby interactable, but never writes aim/spread/accuracy/network state.
- `hit_marker.gd` — a non-stacking typed combat-feedback renderer. Validated elimination feedback takes precedence over an active ordinary hit; gun, melee, and optional hazard event kinds can select distinct presentation without coupling combat code to the HUD.
- `UI/accessibility_manager.gd` — the focused accessibility adapter. It applies UI/text scale, contrast, color filters and optional screen motion blur globally; player/bot/theme code queries it for shake, bob, reduced-motion, and flash policy.
- `kill_feed.gd`, `status_label.gd`, `round_label.gd` — presentation-only, driven by either direct player state or `GameEvents`.
- `player_ui_container.gd` — the per-viewport root that composes the local HUD. After its owner is eliminated it rebinds every `set_player()` child read-only to the current follow target, and restores the owner when spectating ends.

## 10. Splitscreen & Spectating

- `player.tscn` gives each gameplay camera a layer-1 `SpringArm3D`, so map geometry retracts the camera while players/items remain transparent to the collision query. `character_body_3d.gd` rejects mouse-look input whenever `PauseManager` owns a pause overlay.
- Follow spectating inherits the target's spring-arm collision. Free spectating casts a small sphere against layer-1 map geometry before moving. Both spectator input paths stop while the pause menu is open.

- `splitscreen_manager.gd` maintains two `SubViewport`s (P1 left, P2 right), copying each player's camera transform into the corresponding viewport's `Camera3D` every frame. When `GameConfig.split_screen_enabled` is false, P2's viewport is hidden, its renderer is disabled, and P1's stretches full width. Camera synchronization tolerates transient missing players/cameras during scene changes.
- `spectator_controller.gd` takes over after the death animation. Follow mode cycles with LMB/RMB or LB/RB and exposes its current target to HUD binders; Space/A toggles free camera. Free camera uses WASD/sticks and mouse/stick look, Shift/RT up, Ctrl/LT down, and F for fast movement.

- The lobby places **Player Settings** directly below Character Customization and exposes the online-only **The Playpen** entry. The host opens the authoritative practice scene; guests receive a Ready Yes/No prompt before their individual scene-load/ready handshake. The same `player_settings.gd` cabinet is used in the main menu, lobby, and pause overlay. Input-map previews are applied immediately from its pending binding dictionary, Apply persists them, and Cancel/ESC explicitly restores the saved `PlayerPrefs` map so a pause-menu rebind behaves exactly like the standalone screen.
## 11. Menus & Settings

- `main_menu.gd` — page-based (MAIN/MULTI) with animated transitions; owns the live 3D background viewport (`title_bg_map.tscn` + `title_background.gd`).
- `game_setup.gd` — the lobby: map selection, 2–4 team assignment, online ready state, the private One of Us RESIST / LET IT IN choice, Character Customization, Player Settings, and one unified transactional Settings cabinet. The lobby settings slideout presents a concept-matched vertical Overview / Match Flow / Combat / Spawns / Bots / Presets / Testing rail; Bot controls now share the same pending snapshot, Reset, Close/rollback, and Apply path as all match rules. Local setup opens independent P1/P2 previews; online setup edits only the local peer. The Spawns tab keeps gun/melee timing first, then expandable Items, Power Ups, and Melee Weapons pools; their master/per-type state is transactional, preset-backed, and host-synchronized through `GameConfig`. A host-only Testing tab synchronizes `GameConfig.visible_hitboxes` to peers without including it in disk presets. `match_limits.gd` owns the ten-active-actor global cap. Online human capacity is host-configured separately; bots fill only unused match slots and are trimmed as humans join before launch. `map_registry.gd` declares each map's supported capacity, so lobby launch and Random Rotation reject incompatible maps. Online launch uses a synchronized three-second button countdown after an all-ready Start or host Force Start.
- `player_settings.gd` (`player_settings.tscn`) — the single five-category settings cabinet used standalone and as a pause overlay. It edits an isolated pending dictionary; Apply normalizes, atomically saves, then activates it, while Cancel restores every live preview to the opening snapshot. Accessibility contains the internal Shape/Behavior/Feedback crosshair editor rather than navigating to a second scene.
- `player_prefs.gd` — versioned personal-settings source of truth (`version: 3`). The defaults dictionary and `_normalize()` are the schema; migrations merge older files into current defaults. Crosshair arrays/colors are local preferences, never match configuration.
- Before match launch, peer roles may be `lobby`, `playpen_loading`, `playpen`, or host-only `playpen_hosting`. Playpen membership is host-authoritative and filters both MultiplayerSpawner visibility and scene-bound RPC recipients so lobby peers never receive practice actors or combat traffic. Each guest reports scene readiness before becoming visible. Any member can return independently: a guest returns to the lobby scene, while a departing host is removed from practice membership and receives an in-scene lobby overlay as the authoritative Playpen continues serving its remaining peers. Host re-entry reuses that live manager rather than reloading it. The selected match path remains pending so the host can begin normal prelaunch from either practice or the overlay.
- Godot CanvasLayer values are absolute rather than inherited. `game_setup.gd` therefore places its Settings/Customization modal layer twenty levels above whichever CanvasLayer contains the lobby. This keeps the returned host's modal actions visible above the layer-150 Playpen lobby overlay while preserving layer 20 in the normal standalone lobby scene.
- `pause_menu.gd` / `pause_manager.gd` — a context-aware cabinet plus the ESC-routing singleton. Local play sets `SceneTree.paused`; online host/guest menus never pause the tree. Host-only actions are absent for guests. In Playpen context, the ordinary Return/Leave Match row becomes `LEAVE PLAYPEN` for every peer and the host gets `START MATCH`/`FORCE START MATCH`; normal match menus are not changed. Settings and armed destructive confirmation claim ESC before the root menu, with settings ESC routed through the same cancel/rollback method as its Cancel button. Destructive navigation uses `OneGunConfirmButton`'s inline five-second two-click state, not modal dialogs.

## 12. Online Multiplayer

- `NetworkManager` is a transport-neutral session layer backed by ENet/UDP. Tailscale remains an optional listen-host discovery/addressing path, not a requirement of ENet itself. It owns host/join, compatibility negotiation, peer roster/names/roles, authoritative `GameConfig`/map sync, monotonically increasing match and human actor IDs, coordinated scene changes, and match-scene readiness. The build/protocol payload is independent of ENet so a future transport can reuse the same admission contract.
- `build_info.gd` separates player-facing `GAME_VERSION`, compatibility-gating `NETWORK_PROTOCOL`, and artifact `build_id`. Local unstamped runs use `dev`; `tools/stamp_build.ps1` generates ignored `build_metadata.json` with a channel/commit ID before export. Both export presets include that file. Servers log their build and each admitted client build, lobby metadata carries the server build, and the main-menu footer displays the local build. A commit-ID difference is diagnostic metadata and does not by itself reject an otherwise protocol-compatible connection. Game/protocol comparisons return typed rejection reasons so version mismatch, lobby full, and handshake timeout cannot collapse into the same player message.
- `app_bootstrap.gd` is the project entry point. Normal launches route to `main_menu.tscn`; the user argument `--server` starts a headless-capable dedicated session without a local human. The server process remains ENet and gameplay authority (peer 1), while the first compatible remote client becomes lobby controller for settings, roster management, and match start. Controller departure deterministically hands that role to the next connected peer. Dedicated matches reuse the ordinary map/runtime-spawn path but skip client HUD, input capture, and the server-side scene-ready report. The Playpen remains listen-host-only for Phase 1.
- `Dockerfile.server` packages the Linux dedicated export into a non-root distroless image with Tini. The verified Edgegap path pulls immutable private GHCR tags, maps a dynamic public UDP endpoint to container port `24545`, and requires clients to join with `host-fqdn:external-port`. Registry/API credentials stay outside the project and shipped client; Tailscale remains available only as an optional listen-host discovery path.
- Phase 11 dynamic deployment is isolated from the persistent session path. `match_server_context.gd` activates only for a documented Edgegap `MM_MATCH_ID` assignment, validates `MM_TICKET_IDS` plus every `MM_TICKET_<ticketId>` JSON payload, and fails closed on malformed active context. `app_bootstrap.gd` then starts the allowlisted map without the editable lobby. `NetworkManager` requires one unique assigned ticket during the protocol-2 hello, keeps tickets server-only, admits assigned clients as participants without a lobby controller, and waits for all expected participants before gameplay readiness. `tools/run_match_server_smoke.ps1` proves invalid-ticket rejection plus two-client movement/combat while ordinary Windows, listen-host, and `--server` flows remain unchanged. A persistent external coordinator and client endpoint migration are still required because Edgegap Matchmaker does not store One Gun's map/rules/skin/invite lobby state. The staged security boundary is recorded in `docs/MATCH_DEPLOYMENT.md`.
- Online maps reuse the local map scenes without editing them. `round_manager.gd` removes the baked local players, splitscreen and local HUD at runtime, creates `NetPlayers`, and host-spawns one `player.tscn` actor per peer plus the host-configured `DummyModel.tscn` bots.
- A network actor has a sequential match-scoped `actor_id` separately from `owner_peer_id` (the controlling ENet peer). Humans receive 1, 2, 3... by lobby join order; IDs expire and are not reused if someone leaves. Bots use IDs beginning at 10000 and are owned by peer 1. `net_authority_id` remains the Godot replication authority. Names may duplicate; ambiguity-only ID suffixes are presentation, never identity.
- Movement is owner-authoritative and replicated by a runtime-built `MultiplayerSynchronizer` (position, body rotation, aim yaw/pitch, velocity and stamina). Peer 1 is always visible to this movement synchronizer because a dedicated server is intentionally absent from the human roster but still needs current transforms for authoritative pickup/combat validation. A host-authority `SpawnVisibility` synchronizer filters replicated actor roots for other peers by lobby role: waiting-room peers receive no gameplay actors, while active participants and accepted late spectators do. Match RPC broadcasts use the same role filter. Before match actors are despawned for a lobby return, each owning client suspends its movement publication so in-flight deltas cannot target removed `NetSync` nodes. Gun pickup, firing, bullet hits and elimination are host-resolved and round-epoch guarded.
- Online gun requests and broadcasts route through the stable map-owned `RoundManager`, matching the existing melee/item coordinator pattern. The gun itself is reparented between the map and a holder's hand, so sending RPCs from the moving gun node can produce different node paths on the server and clients. Reload completion is broadcast by the host through the same coordinator. Bullets carry the round epoch that created them, so a late collision cannot eliminate an actor after the match has advanced to a different round.
- Online melee uses `round_manager.gd` as a stable RPC coordinator because `melee_weapon.gd` can be reparented between the map and a player's hand. Every authored `melee_spawn_point` is populated at round start and independently schedules a randomized replacement 5s after a successful pickup, using a fresh candidate ID. At OT start the host chooses and synchronizes the single active melee supply assignment while carried melee remains attached to its holder. The host synchronizes each identity and validates pickup, swing, drop, throw, hit, disarm, breaking, and reset actions through that ID. Throw launch preserves world scale after reparenting, starts clear of the body, and uses an explicit 0.40s thrower collision exception; in Playpen, the coordinator retires a loose landed/dropped melee instance after 2s.
- Online items use the same stable `RoundManager` coordinator because they are reparented into either of a player's two item slots. Every authored `item_spawn_point` and `powerup_spawn_point` is preserved; the host rolls assignments and broadcasts exact marker transforms. Successful pickups schedule fresh randomized IDs after 8s. Pickup distance/LOS, drops, throw aim, grenade prime/remaining fuse, Flash Camera validation, powerup collection, Extra Life, Sticky Hands, Reach and deployed gameplay effects are host-resolved. Clients simulate thrown visuals, but the host broadcasts final deployment/effect results. Deployed instances use host-issued IDs so trap/pad/decoy presentation events address the same object on every peer. Practice-mode item drops retire after the existing 2s return delay, and loose practice guns use the same manager-owned cleanup/replacement rule.
- Host/join always tears down an earlier ENet peer first. A newcomer remains in `_provisional_peers` until its reliable client hello returns matching game-version/network-protocol fields plus its informational build ID within 5s; only then is it added to `peers` and broadcast in the roster. A mismatch returns a typed reason and detail, resets the client peer, and displays the `VERSION MISMATCH` restart/update dialog without entering the lobby or emitting partial gameplay RPCs. Ordinary joins fail cleanly after 12s. Match loading has a 30s readiness deadline with per-peer status, client retry, host removal of failed peers, and return-to-lobby recovery. The host advertises its lobby name, version, protocol, and build ID on UDP 24546 across the current Tailscale peer list; direct `100.x` remains a fallback. Each peer may rename only itself while in the lobby; names lock once that peer enters a match role.
- One of Us volunteer intent is deliberately absent from lobby roster entries and network snapshots: NetworkManager keeps a host-private peer dictionary, accepts only each sender's own reliable preference RPC before launch, and exposes only the selected role dictionary after the server draw. Lobby roster entries include a sanitized `skin_id`. Client hello and lobby skin-change RPCs send the local choice to the host; authoritative lobby snapshots echo it to every peer, and `RoundManager` includes it in each human spawn payload. A person joining during a match receives a waiting-lobby role and is never inserted into the active roster. They may remain there or request pure spectator loading, which grants replicated actors, follow/free camera, scoreboard access, and the followed actor's complete read-only combat HUD for every remaining round without combat, scoring, or spawn participation. Match end returns everyone to the normal lobby.
- Online FFA and 2–4-team matches use the same host-authoritative scoring, friendly-fire policy, bot team assignments, round resets, and HUD. Online bot count/difficulty is host-configured and capped so active humans plus bots never exceed ten; only the host runs bot AI/physics while clients render synchronized puppets. The online ESC overlay never pauses `SceneTree`: hosts can return everyone to lobby/main menu, while a client can leave without ending the host session.

## 13. Data-Driven Patterns Worth Preserving

- **Input prefix pattern**: all input reads go through `input_prefix + "_action"` — new player-specific actions must follow this convention or splitscreen will silently break for one player.
- **Interactable registration**: pickup objects register themselves into the player's `nearby_interactables` array rather than the player scanning the tree — new pickup types should follow this registration pattern to stay consistent with gun/melee/item pickup.
- **`pick_up()` returns success/failure, not void**: since §6's rework, every pickup-able object's `pick_up()` returns `true`/`false` so the caller can tell whether anything happened — required for the player's tap-vs-hold decision. Any new pickup type must follow this contract.
- **Tier stats as data, not code branches**: `melee_weapon_registry.get_stats_for_tier()` computes tier scaling from multipliers rather than hardcoded per-tier stat blocks — adding a weapon means adding one `_build_x()` function, not touching tier logic.
- **GameConfig as single source of truth for rules**: UI (lobby toggles), gameplay (round manager, weapons), and persistence (presets) all read/write the same autoload fields — avoid shadowing these values locally in gameplay scripts.
