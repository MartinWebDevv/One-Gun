## 2. Scene Flow

```
main_menu.tscn  →  game_setup.tscn (lobby)  →  <selected map>.tscn (match)  →  back to main_menu.tscn
                                                        │
                                          RoundManager (per-map Node) drives
                                          round/set/match state for that scene
```

- Maps live under `maps/test/` (`NewMap.tscn`, `NukeTownMap.tscn`) plus a root-level `node_3d.tscn` (Coliseum-style arena) and `title_bg_map.tscn` (used only as the main menu's live 3D background).
- Each map scene contains its own `RoundManager` node instance (`round_manager.gd`), spawn-point markers (`spawn_point` group), and a `gun_spawn_point` group for `"random"` gun spawn mode.
- Player instances come from `player.tscn`; bots are spawned at runtime from `DummyModel.tscn` (`dummy.gd`) by `RoundManager._spawn_bots()`.
- Online lobbies can branch into `maps/playpen/playpen.tscn` before launching a match. `playpen_manager.gd` subclasses `RoundManager` only to reuse actor/item/melee RPC contracts; it suppresses round scoring/timers, creates the procedural retro-space arena, manages infinite respawns, and owns three deterministic armory bays. Guests may return to `game_setup.tscn` without ending the practice session; the network host owns the authoritative room and closing it returns every remaining member to the lobby.

## 3. Player Architecture

`character_body_3d.gd` (attached to `player.tscn`, a `CharacterBody3D`) is the single script driving both P1 and P2 in splitscreen. Instances retain separate `input_prefix` values (`"p1"` / `"p2"`), while `use_gamepad_look` is resolved at runtime from the saved primary-device choice for P1 and the dedicated-controller rule for P2. Every `Input.is_action_*` call is still built as `input_prefix + "_action_name"`, so splitscreen support remains one shared controller script rather than parallel player implementations. `PlayerPrefs` rebuilds the InputMap from authored defaults plus saved overrides, filters P1 to the selected device group, keeps P2 controller-only, and assigns distinct physical joypad IDs when both local players use controllers. Its joypad connection handler reapplies routing after hot-plug events.

Bots (`dummy.gd`) are a **separate script** from the human controller, not a subclass or a shared-base-class specialization — they reimplement movement/combat decisions independently, driven by a difficulty-tuned decision loop (`_decide_objective`) instead of input polling. This means gameplay-affecting tuning (speed, stamina, dash) that lives as `const` in `character_body_3d.gd` must be mirrored by hand in `dummy.gd` if it needs to match; there's no shared base class enforcing parity.

Bot pathfinding uses the `NavigationAgent3D` in `DummyModel.tscn` and one baked `NavigationRegion3D` per gameplay map. City, Forest, Western, Neon Circuit, and Trippy Mountains keep their baked polygon data in `navigation/*MapNavigation.tres` so scene edits cannot silently leave an empty inline `NavigationMesh`; `tools/bake_existing_navigation.gd` rebuilds those resources directly from each map's static colliders. Neon Circuit's region is top-level and bakes in world space, producing the current 611-polygon mesh without inheriting the scene root's 2× presentation scale twice. Trippy Mountains scales the partner environment 2.3× around `PlayArea`'s center and generates one backface-safe static trimesh from every visible asset mesh intersecting that rectangle. The world-space navigation bake includes those merged obstacles and filters the otherwise oversized flat ground to the four authored boundary barriers. Its generated marker layout samples that baked ground against live physics, reserves a 2.5 m obstacle-free radius at every marker, distributes ten player starts in angular sectors, and uses farthest-point spacing for all pickup slots. Its lobby camera orbits only a narrow arc from inside the mountain ring, its main-menu camera uses a matching enclosed pan, and its registered carousel thumbnail is captured from that real stripped map preview. NukeTown retains its inline bake. All maps expose player/bot starts through the shared `spawn_point` group. `dummy.gd` applies a 1.0 m `path_height_offset` so floor-height path points align with the bot body's movement plane and reached waypoints advance correctly.

Reusable City building variants `models/cityAssets/BuildingC_Enterable.tscn` and `BuildingB_Enterable.tscn` wrap the original GLBs without replacing them. Each has permanent front and right-side openings, one open playable ground floor, solid transparent window colliders, full upper-shell/roof collision, and navigation entry markers. No current City-map instance references either variant until an authored placement is chosen and the City navigation resource is rebaked.

Key subsystems inside `character_body_3d.gd`:
- Movement/physics (`_physics_process`): walk/jump/dash plus sprint/stamina code. The match-wide `GameConfig.sprinting_enabled` setting gates sprint for both humans and bots and defaults off. Human jump impulse is exported as `jump_velocity`; there is no post-landing timer gate, so the raw grounded state is the only normal re-jump requirement. The separate 0.12s terrain-floor grace affects animation selection only. A manhole launch establishes a separate steam-flight state on human and bot controllers. Spring pads use a different state: 13.0 vertical launch, a first-input 1s window for a committed 4.0 horizontal boost, and a 60% blend toward normal air steering until landing. Maple & 3rd's `HydrantWaterPush` tests actor positions against the map-authored nozzle-side `CollisionShape3D`, waits for ordinary upward jump velocity, then applies a 15.0 m/s impulse toward a separate `LaunchDirection` marker. Human and bot controllers decompose their existing horizontal velocity into with-stream and cross-stream components: perpendicular and with-stream motion survives, while opposing motion retains 25% before the impulse is added. A water-specific airborne floor then preserves at least 40% of the impulse's horizontal stream speed against opposing air input without touching the perpendicular component. Vertical velocity uses the greater of the current rise and the water arc, avoiding jump-force stacking. Separating trigger geometry from launch direction preserves level-editor collision adjustments and prevents the particle emitter's visual rotation from creating sideways gameplay force. The water launch otherwise uses the same steerable air state. An airborne dash explicitly clears either pad or water momentum before applying the dash, preventing launch force from stacking with dash force. Outside those explicit spring, steam, and hydrant states, both human and bot controllers clamp unintended upward launch velocity to 12 m/s so a combat impulse cannot send an actor indefinitely skyward. The host sends all launch contracts to online actors; decoys implement the non-dash spring contract as well.
- Weapon/item slot management: `active_slot` state (`"none"` / `"weapon"` / `"item1"` / `"item2"`), `get_hold_point()` / `get_melee_hold_point()` / `get_item_hold_point()` node lookups for attaching held objects. Rendered players resolve the animated sockets under `CharacterModel`; dedicated-server players lazily create invisible gameplay-only `Marker3D` sockets under `AimPivot`, ensuring authoritative held objects remain in the active SceneTree even when presentation nodes are unavailable. Pickup code validates the target socket before detaching an object from the world, so a missing socket cannot orphan the gun, melee weapon, or item. See §6 for the full pickup/swap/hold-drop architecture.
- `nearby_interactables`: normally populated by pickup Area3Ds registering themselves (`register_interactable`). Reach adds a throttled 7m, line-of-sight scan of gun/melee/item/powerup groups and merges those candidates into the same array; powerups collect on contact with that scan while other pickups still require Interact. Host pickup validation uses the same `GameConfig.REACH_POWERUP_DISTANCE`. A simultaneous Fire+Interact conflict is resolved in favor of Fire so attacks cannot pick up nearby objects. During a Reach swing, the shared melee capsule is extended and shifted outward so its near end remains at the holder and its far end reaches 7m; local and host hit resolution both enforce that same maximum instead of the universal 5.2m normal cap.
- Status effects: knockback, stagger, slow, flash blindness, bullet immunity, disarm-shield, Reach, and Fast Hands — implemented as timers/flags on the controller itself and mirrored explicitly in `dummy.gd` where bot parity matters.
- Human visual/animation runtime: `player.tscn` can swap between eight registered wrappers: the public Male and Female cats plus the developer-gift-only Gold Fish Bag Man, Eye Wizard, Mr. Mushroom, Mr. Poop, Mr. Salt, and Spooky Witch characters under `models/player_v2/characterSkins/`. Each wrapper normalizes its authored scale and facing while preserving its own material and target skeleton/rest profile. All expose the same 33 core Mixamo bone names and socket contract; extra character-specific bones remain in authored rest beneath the retargeted hierarchy. `player_v2_visual.gd` bakes each named `animations/*.fbx` clip at 30 fps as source-rest-relative deformation reconstructed against the selected model's target rest pose; static animation/profile caches are keyed by model ID so no body shape corrupts another. Horizontal Hips travel is stripped while authored vertical motion remains. Gameplay players request the core movement/combat set, menu previews request Idle, and decoys request Idle plus Standard Run. Every model deliberately uses the Male V2 clip as the master idle. The 14 optional podium/round clips are registered by stable ID but retargeted and cached only when an equipped or previewed move requests one.
- `player_v2_visual.gd` also publishes scale-normalized top-level left/right sole sockets sampled between the animated Mixamo foot and toe bones while retaining character-facing axes. The split_spring_shoes tool separates the authored pair at its Z=0 center plane into two complete recentered GLBs; the wearable scenes orient one full shoe per paw and keep both spring coils vertical beneath the sole. Equipment follows those sockets without inheriting the imported rig's oversized skeleton scale or moving the gameplay camera.
- Human appearance runtime: `player_skin_registry.gd` is the stable model-ID, skin-ID, display-name, gender-specific texture, portrait, visual-scene, and headwear-compatibility registry. Male/Female are the only always-available public model choices. Gold Fish Bag Man, Eye Wizard, Mr. Mushroom, Mr. Poop, Mr. Salt, and Spooky Witch are developer-gift-only models resolved from owned `character_model` loadout items; they are never public selector or Prize Counter choices. These authored characters keep their fixed materials and hide cat-color editing. Every registered model must define an animated headwear socket profile plus an explicit per-Hat fit fallback chain in `MODEL_HEADWEAR_PROFILES`; validation rejects a future model that omits this contract. `models/cosmetics/hats/hat_cosmetic_registry.gd` separately maps stable Hat IDs to optimized local GLBs and shared/per-model fit data; optional editor-authored overrides live in `models/cosmetics/hats/hat_fit_profiles.tres` and merge over those conservative registry defaults. Exact per-model overrides win, then the declared compatible-model chain is checked, so existing manual adjustments remain active until a dedicated fit is saved. `tools/hat_fitting_tool.tscn` discovers every `MODEL_IDS` entry, previews its real visual and HeadwearSocket, keeps drafts in memory until an explicit save, cycles destinations with Copy to Next Model, and edits only that small override resource—never a source/runtime GLB. Its operating, future-model, and recovery procedure is documented in [HAT_FITTING_TOOL.md](HAT_FITTING_TOOL.md). `character_cosmetic_binder.gd` owns the common wearable path: rigid Hats, glasses, earrings, backpacks, and similar props mount beneath a semantic `BoneAttachment3D`, while shirts, pants, and other deforming garments must ship as a named-bind `Skin` authored for the selected character skeleton and are redirected to that live `Skeleton3D`. Incompatible or unnamed garment binds are rejected instead of silently floating. Current approved Hat offsets are preserved inside the bone-bound `HeadwearSocket`, and the engine follows the bone without a Hat-specific per-frame script update. `wearable_cosmetic_registry.gd` is the trusted local ID/mode/socket/path map for future art. The **Locker** uses one isolated manually rotating 3D preview, a two-button public Male/Female grid beneath it, and a 5/5/3 grid of static cat-color portraits generated by `tools/generate_character_portraits.gd`; owned developer-gift models use their supplied portraits in separate preview/equip rows. Its Character / Weapons / Victory / Audio areas list authenticated owned items only, with deeper skin, color, clothing, outfit, Headwear, weapon-skin, pose/dance/move, and Winners Circle filters; absent local artwork remains a safe `ART PENDING` identifier. Hat cards and inspectors instantiate the same actual local model used in gameplay for true 3D previews. Prize Counter hats use an adaptive shoulder-up camera derived from the selected hat's rendered bounds; Locker and progression hats keep full-body framing and derive both center and distance from live character/Hat bounds. All three leave top clearance during the shared idle. Drag/right-stick input rotates only the character pivot while the camera, lights, podium, and background remain in fixed world space. Locker, Prize Counter, and progression Hat previews play the shared idle while visible. P1/P2 keep independent pending model+color pairs. Back/Escape discards them, while Save & Close atomically commits to `PlayerPrefs`, session-only `GameConfig.player2_model_id`/`player2_skin_id`, or `NetworkManager`. Online peers synchronize only stable IDs and resolve textures/portraits locally. `CharacterPortrait` supplies the main-menu profile card and human lobby rows.
- Persistent cosmetic progression: `SupabaseManager` reads authoritative ownership/loadout state and `supabase_cosmetic_registry.gd` maps stable database IDs to safe local visuals. Its character-visual seam applies the equipped character skin plus all wearable slots to gameplay and presentation actors through the shared skeleton binder. Local P1 listens for loadout refreshes, while `NetworkManager` relays sanitized equipped IDs in the existing online roster and `RoundManager` copies them into human spawn data, so each locally mapped wearable resolves identically on home, local gameplay, and every online peer. Missing art stays data-only and cannot become a server-selected resource path. Auth tokens, currency, and inventory never enter ENet payloads. See [SUPABASE.md](SUPABASE.md).

- Gun-holder and reveal presentation: other players see a line-of-sight-gated `GUN HOLDER` billboard plus a pulsing depth-tested Fresnel rim applied only to bound character skin meshes. Overtime and the 0.5s decoy-destroyer reveal use a through-cover variant of that same real-surface rim. None of these paths expands an inverted hull, so the heavily scaled V2 import cannot become a solid shell and held equipment is unaffected. Temporary reveals explicitly clear their overlay before restoring any applicable gun-holder rim; this matters in local play, where the gun holder intentionally has no shared mesh rim. The holder never sees their own gun-holder marker.

- Gift-character size/collision contract: the six developer-gift visual wrappers are uniformly normalized to the 2.6453-unit midpoint of the two approved cat rigs and grounded at the shared capsule bottom. Model swaps replace only `CharacterModel`; every human continues to use the one `player.tscn` capsule (`radius 0.495`, `height 2.3266993`) outside that visual subtree. `PlayerSkinRegistry.MODEL_IDLE_ACTOR_BOUNDS` stores validated idle-pose actor-space envelopes for all registered models so home/preview framing remains accurate for skinned meshes without CPU skinning or scanning every vertex at runtime. `tools/character_size_hitbox_validation.tscn` rejects size, grounding, envelope, or shared-collider drift.

- Human animation state is owned by character_body_3d.gd and always applied through each wrapper's explicit get_animation_player()/ensure_animation_library() API, never a recursive child search that could select a cosmetic's player. Imported autoplay is stopped before the shared named library takes control. Grounded state is sampled after move_and_slide() in normal, paused/chat, intro, stagger, and knockback branches; respawn immediately publishes shared Idle so local players and online puppets cannot remain in Fall after landing or reset.

## 4. Weapons Architecture

- `weapon_data.gd` — a `Resource` subclass holding a melee weapon's static handling stats (windup/active/recovery base times, stamina cost, raw model length, model-local grip anchor, held orientation/scale, and model path). `melee_weapon_registry.gd` constructs one `WeaponData` instance per weapon type at `_ready()` and hands out random picks. It divides the shared 1m held-length target by each measured raw model length, preventing differently authored source units from making one weapon appear tiny. Each grip anchor maps the imported handle base to the V2 paw socket. Model-local `HitShape` authoring helpers are ignored at runtime; `melee_weapon.tscn` owns one forward-facing 0.45m-radius capsule used by all five models. It extends 5.2m from the paw in every mode and 7.0m during Reach. Every type now uses the Frying Pan's 0.32/0.28/0.55 authored phase timing while preserving its own stamina cost. The character's authored melee animation supplies all visible swing motion; the weapon's physics-phase sequence only opens/closes the hit window and handles recovery.
- `melee_weapon.gd` (on `melee_weapon.tscn`) is the generic scene used for every weapon/effect combination the registry rolls — the model, base handling, and effect are applied onto each instance rather than requiring 5 separate weapon scenes. Tiers are retired; extra tier keys in stale dictionary payloads have no reader or runtime effect. Runtime phase times are the authored values ×0.85, then divided by 1.5 while Fast Hands is active; stamina does not change. `MeleeWeaponRegistry.get_random_weapon_data()` filters through `GameConfig.melee_weapon_registry`; config normalization and the lobby both guarantee at least one enabled type. `RoundManager` populates every authored melee marker at round start and schedules that marker's fresh randomized instance 5s after its weapon is picked up. On OT transition, held and already-dropped melee remain pickable, regular placements are retired, and one supply is moved to the exact map center while continuing the same refill contract.
- `gun.gd` (on `gun.tscn`) is a `RigidBody3D`: physics-frozen and parented to the holder's hold point while held; explicitly unfrozen **and awakened** when dropped on swap/death/disarm so gravity carries it into world geometry; `reset_to_spawn()` each round. Online drops synchronize the release position, then every peer simulates the same gravity-driven fall instead of freezing the gun in mid-air.
- `bullet.gd` (on `bullet.tscn`) is fire-and-forget: instantiated by `gun.fire()`, travels at a fixed speed, checks `GameConfig.can_affect()` (teams/friendly-fire) and target bullet-immunity, then eliminates and frees itself on contact. Human shots start on the camera viewport's exact center ray at the stable actor/aim-pivot plane, never at the animated shoulder-offset muzzle; camera-less bot shots still originate at the physical muzzle and use their configured aim/spread. The readable 0.1m visual sphere has a tighter 0.025m collision core.

- Human gunfire samples viewport-local center coordinates once for a direction/origin pair from the `Camera3D` that actually renders that player's `SubViewport`, not the mirrored source camera. `splitscreen_manager.gd` refreshes the render camera and all projection properties when the shot is requested; `Camera3D.project_position()` places the bullet's first world point on the exact crosshair pixel at the stable actor/aim-pivot depth. The animated gun and muzzle are visual-only for human aim and cannot shift this origin. The body receives that local transform before it enters the scene/physics world, stays hidden until launch, and resets physics interpolation before its first visible frame, so every point remains on one ray with no shoulder-offset convergence. Online owners send the exact pair; the host validates the origin is within the legal third-person camera envelope around the authoritative actor and preserves it rather than mixing it with a delayed host camera transform. Server-owned bots still originate at the physical muzzle.

## 5. Items & Powerups Architecture

- `item.gd` (`item.tscn`, `grenade.tscn`) — generic held/throwable consumable container, data-driven via `item_type` + `deployed_scene`. Fire press/release is split into `begin_use()` / `release_use()` so all ordinary throwables can preview while held and commit on release. Grenades specialize this path: `fuse_time` starts at Fire press, the use becomes non-cancellable, remaining fuse is preserved through the authoritative throw, and expiry can deploy directly from the holder's hand. Other positive-fuse items still begin their fuse after release. Marker-authored items claim their independent 8s randomized refill when picked up; the carried instance retires after use, preventing a duplicate refill.
- `bubble_gum_trap.gd` (`bubble_gum_trap.tscn`) — the deployed hazard instance spawned when a thrown item lands; owns its own **lingering** Area3D slow effect and respawn timer, independent of the item pickup itself. Stays live until players walk into it or its lifetime expires.
- `grenade_explosion.gd` (`grenade_explosion.tscn`) — a **one-shot** 7.5m query, not a lingering hazard. On `_ready()` it applies team-aware knockback with linear 4.0→2.0 center-to-edge falloff, including self-effects, then frees itself. Online uses the same falloff through `RoundManager`.
- `smoke_cloud.gd` (`smoke_cloud.tscn`) — a 5m-radius, 4.2m-half-height ellipsoidal concealment volume rather than the former sphere. Presentation uses overlapping camera-facing procedural smoke masks: alpha-scissored inner wisps prevent scenery bleed-through, while densely layered moving outer wisps restore a soft, irregular silhouette. It changes bot/visibility line-of-sight but has no collider, so bullets continue through it.
- `decoy_body.gd` (`decoy_body.tscn`) - a self-contained `CharacterBody3D` combat target with a 10s authoritative lifetime. Its visual uses the owner's selected Male/Female V2 scene and color, then switches between in-place Idle/Standard Run clips; the procedural gait remains only as an import-failure fallback. Movement, combat-target, team-protection, bot-targeting, trap/status, shooter-reveal, identity-tag, and synchronized online action contracts are unchanged.
- `double_jump_shoes_item.gd` (`double_jump_shoes.tscn`) — a use-in-place `item.gd` specialization. Activation consumes the carried instance and attaches the split left/right shoe scenes to the actor feet on every peer. The controller holds one boolean charge; an accepted mid-air Jump applies 50% of normal jump velocity, plays the boing SFX, removes both attachments, and is host-confirmed online. A player may carry another pair while one charge is active, but cannot activate the second until the first is spent.
- `flash_camera.gd` (`flash_camera.tscn`) — an `item.gd` specialization with no throw path. Its first Fire enters a framed local camera overlay and its second requests a photo. Local/host validation shares the 30m range, 60° view/facing cones, viewport frame, line-of-sight and `GameConfig.can_affect()` checks; accepted targets receive a distance-scaled 6s→3s flash whose first 2s are opaque white before a linear fade over the remaining duration. The viewport-scoped overlay safely supports human, bot, and followed-spectator HUD targets. The shipped mesh is procedural placeholder art so a final model can replace the scene visuals without changing gameplay.
- `powerup.gd` (`powerup.tscn`) — marker-spawned pickup with a fixed type until collection. A transparent, nearest-filtered `Sprite3D` selects one of seven cached 64px icons and billboards per camera, including each splitscreen viewport; the existing billboarded `Label3D` remains above it. Fast Hands resolves to the shipped `fastHands2D.png`. Contact applies the effect to the player (`apply_powerup()` on the controller), then the marker re-rolls and respawns after 8s. Local and synchronized online respawns update the texture and label together. Both local rolls and host-authored online assignments use `GameConfig.enabled_powerup_types()`; an empty pool produces no placements.
- `powerup_status.gd` — pure UI, listens for active powerup state on the local player to render the countdown stack; not itself a gameplay system.
- **Throw arc**: `item.gd` and `melee_weapon.gd` expose the actual launch origin/velocity/gravity to `throw_arc_overlay.gd`. The overlay simulates only a short dotted portion, stops at the first physics collision, and intentionally has no landing marker. It binds to the local actor or current follow-spectator target. Release uses the same data, keeping the preview honest; Flash Camera overrides the interface to disable it.

## 6. Pickup / Interact / Swap Architecture

The interact button drives all pickup, swap, and voluntary-drop behavior through one per-frame decision in `character_body_3d.gd._physics_process()` — see `docs/GAME_RULES.md` §9 for the player-facing behavior this implements.

- **`pick_up()` returns a `bool` now, on every pickup-able object** (`gun.gd`, `melee_weapon.gd`, `item.gd`) — `true` if the pickup/swap happened, `false` if it refused. This is the core contract: `character_body_3d.gd._try_interact()` just loops `nearby_interactables` calling `pick_up(self)` until one succeeds; it does not pre-compute eligibility (empty slot? valid swap? gun exception?) — each object decides for itself and reports back. Any future pickup type should follow this contract rather than having the player special-case it.
- **Human pickup calls carry an explicit Interact transaction gate**: `_try_interact()` raises `_manual_pickup_request_active` only around its synchronous `pick_up()` calls, and gun/melee/item entry points reject a human controller when that gate is closed. `Area3D.body_entered` remains registration-only, so a proximity callback can never equip or swap an object. Bots intentionally lack this human-only gate and retain their direct AI pickup path; authoritative mode loadouts continue to use `_local_pickup()`/`_do_pickup()`.
- **Tap vs. hold** is resolved once, at press time: if `_try_interact()` returns `false` (nothing nearby could be picked up/swapped), the press starts a hold timer (`interact_hold_active` + `interact_hold_timer`, threshold `INTERACT_HOLD_DROP_TIME` = 0.5s); crossing the threshold while still held fires `_drop_active_slot()` once. If `_try_interact()` succeeds, no hold timer starts at all — holding the button afterward does nothing.
- **Swap-in-place**: when an object's `pick_up()` needs to bump something the player already holds (melee-for-melee, melee-for-gun, item-for-item), it captures its own `global_position` before anything moves, calls `.drop()` on the old object, then repositions the old object to that captured spot. This is what makes the displaced item land exactly where the new one was instead of at the player's feet.
- **The gun exception is enforced in `melee_weapon.gd`, not the player**: `pick_up()` returns `false` immediately if `p.holding_gun` is true, with no auto-drop. Putting this at the object level (rather than only gating it in the player's input code) means it can't be bypassed by another caller — bots included, even though they call `pick_up()` directly with no tap/hold concept at all.
- **Item slots are dual, weapon slot stays singular**: `character_body_3d.gd` exposes `held_item_1`/`held_item_2` plus a small interface — `can_pick_up_item()`, `assign_item()`, `clear_item_slot()`, `get_active_item()` — that `item.gd` calls generically instead of touching slot fields directly. `dummy.gd` (bots) implements the same method names against its own single `held_item` field, so `item.gd` has one code path for both: `if p.has_method("can_pick_up_item"): ... elif "held_item" in p: ...`.
- **Bots bypass the tap/hold system by design, not oversight**: `dummy.gd` keeps a simpler single-`held_item` model and calls `pick_up()` directly — every bot pickup is effectively an instant tap. The gun exception above still protects bots as a free side effect, and bots additionally already gate their own melee-pickup attempts on `not holding_gun` before ever calling `pick_up()`.
- **Both item slots share one physical attachment point**: there's no second `ItemHoldPoint` node on the character model, so `held_item_1` and `held_item_2` both parent under the same node when held. `_update_active_slot_and_visuals()` toggles each held item's `.visible` individually based on which slot is active, so only one item is ever rendered in-hand even though both are legitimately held.

## 7. Round/Match State Machine (`round_manager.gd`)

The state path is `"countdown" -> "live" -> "overtime" -> "ended"` when the adjustable round timer expires with multiple survivors; otherwise live play proceeds directly to ended as before. The timer accepts whole-second values from 1–900, while 0 keeps the unlimited option. OT boundaries are centered on the midpoint of authored gameplay markers rather than assuming the gun spawn is the map center. Future maps can override the inferred footprint with `overtime_boundary_point` markers and the inferred midpoint with one `overtime_center_point`. The axis-aligned X/Z extents are shared by damage and visuals, and damage deliberately ignores Y so elevated players above unsafe floor remain exposed. The visual fire is generated from the first non-empty baked `NavigationRegion3D`; if a bake is absent, `round_manager.gd` emits a warning and builds an emergency projected-floor surface rather than leaving lethal ground invisible. Survivor reveal pulses use a depth-free Fresnel rim on character skin meshes only, so the V2 model remains recognizable through cover without expanding into a scale-dependent solid shell or including held props.

The manager owns a 5s opening approach followed by an uninterrupted inward close that fully engulfs the arena at about 2:00. At OT start, it copies the map's baked `NavigationMesh` polygons into a slightly raised visual-only mesh. A world-space shader reveals only the unsafe portion of that continuous playable surface, independent of whether the underlying imported mesh, CSG or Terrain3D material accepts decals. Deduplicated navigation vertices and triangle centroids feed one high-rate, short-lived `CPUParticles3D` emitter, adding fast-rising vertical flames at the same active boundary. Valid unsafe-floor points are assigned before the emitter starts so it cannot create a fallback particle at the arena origin. A 0.35-unit visual lead guarantees the floor becomes visibly dangerous before exposure begins. Because a baked navigation region is already mandatory for game-ready maps, future maps automatically use this path. The same manager owns exposure counters, zone pulses, Standard/Chaos gun rules, and millisecond-resolution tiebreak data.

- Dispatches mode-specific round setup from `GameConfig.game_mode`. All Gun replaces the shared gun with personal guns plus synchronized three-heart state rendered both in HUD and as depth-tested filled/empty Label3D markers above every actor, removes ground melee, filters Extra Life from its spawn pool, converts disarms to reloads, grants 1s protection when combat opens and after each nonlethal gunshot, and makes OT fire immediate sudden death. One of Us asks each human for a session-only private volunteer preference, lets the host choose randomly from that private pool (or all participants when empty), synchronizes the resulting host-selected role dictionary before loadout/reset, grants Us three base dashes plus personal guns and Them four base dashes plus personal Frying Pans, owns 1.5s conversion and 2.0s infected respawn generations, filters temporary spectator targets by role, awards the final Us one fourth single-use dash, and resolves the fixed 180s role win condition as a winner-takes-all match without sets or OT. Its bot target policy always seeks the nearest opposing role, with Them hunting into melee range and Us retreating toward gun spacing while maintaining line-of-sight fire. A duplicated runtime Environment supplies the darker/desaturated/cool-fog grade only for this mode, leaving authored map resources untouched.
- `one_of_us_intro.gd` is the modular 7.35s hunt cinematic layer: camera route stages, target-scan count, timings, text, FOV, glitch strength, and optional audio cue are tunable constants in one script. It builds a temporary camera above the arena, deterministically scans actors, dives behind the host-selected first infected, triggers their synchronized transformation, and runs a tightening unstable orbit. Role-specific endings either push through the infected into their body-look gameplay view or throw a survivor camera backward and sweep it to the local shoulder before transitioning home. `character_body_3d.gd` supplies the camera handoff and retains an input lock through the shared deadline; `one_of_us_role_visual.gd` supplies the non-blob infected rings, particles, and light pulse. The ordinary map intro path is unchanged for other modes.
- `winners_circle_match_result.gd` converts live and departed actor dictionaries into one frozen, non-sensitive result snapshot. It copies stable appearance/cosmetic IDs, final stats, finish/DNF and forfeit flags, the locked starting/finishing roster counts, activity eligibility, a unique match ID, ruleset/map IDs, and each participant's random reward claim hash. Finishers sort ahead of DNF entries; the known champion is forced first, with the normal round-win/finish/stat tie-break chain afterward. Account tokens, Supabase user IDs, balances, inventory, and private claim secrets never enter this snapshot.
- `WinnersCircleCoordinator`, created under the stable `RoundManager` path on every peer, broadcasts that snapshot and owns ready requests, disconnect-aware required-peer state, the 10s server-side minimum, synchronized all-ready return countdown, and host override. In a dedicated session, the human lobby controller receives the moderator control and routes Return All reliably to authoritative peer 1. The full-screen overlay registers as the exclusive modal input owner while present, so live spectator LMB/RMB/gamepad handlers and persistent chat cannot consume Ready/Return events before GUI dispatch. There is no automatic results timeout. Official eligibility locks from the three-plus authenticated starting roster. Remaining finishers privately submit a canonical snapshot and their own claim secret; presentation-only viewer identity is removed at the client and Supabase boundaries before the shared hash is calculated. Supabase uses the finisher majority, including a one-confirmation sole-finisher forfeit, then merges the authoritative idempotent receipt. Ready/return timing is independent of reward settlement.
- `match_reward_calculator.gd` is the shared deterministic display/test calculator for the locked Beta formulas: 20–100 performance XP, placement-only 250/200/150/100 Gun Tokens, one winner Trophy, the gradual Season XP curve, and flat 400-XP Career levels. PostgreSQL recalculates every persisted value and atomically grants the first Official Classic victory of each UTC day an additional 25 Season XP plus 100 Gun Tokens. The client preview can mark that check as pending but never writes a balance, decides the daily state, or makes a result Official.
Owns a single `round_state` string machine: `"countdown" → "live" → "overtime" → "ended"` (repeating per round), plus `round_number`/`set_number` counters and per-player dictionaries (`round_wins`, `match_points`, `stat_kills`, `stat_deaths`, `stat_disarms`, `stat_pickups`, `stat_melee`). It:
- Runs the first-round-only 3s introduction before countdown, reading one optional `round_intro_camera_point` from the active map plus an optional synchronized orbit-angle override from the active map and asking each human actor to orbit from it toward that actor's spawn. The default remains 180°; Trippy Mountains uses a 40° interior-only sweep. Actors remain frozen; Reduced Motion takes the fade-only branch.
- Spawns bots at `_ready()` from `GameConfig.bot_configs`.
- Filters players to those relevant to the current mode (drops P2 if splitscreen is off).
- Subscribes to `GameEvents` (`player_eliminated`, `player_disarmed`, `gun_picked_up`, `melee_hit_landed`) to update stats — **this is the only consumer of most of these signals for scoring purposes**; UI systems (kill feed, HUD) subscribe to the same signals independently for presentation.
- Computes scoreboard data on demand (`get_scoreboard_data()`), sorted by sets then rounds, including presentation-only host/bot/current-gun-holder markers.
- Drives round/set/match end transitions and countdown timing, using the `@export` timing vars as the single source of truth for banner durations. It additionally records total round wins plus second/third round finishes for post-match FFA placement.

## 8. Global Event Bus (`game_events.gd`)

A minimal autoload with no listener/emitter registration logic — pure pub/sub. Actor-keyed signals are authoritative for scoring and combat feedback; legacy name-keyed signals remain for presentation-only consumers:

| Signal | Emitted by | Consumed by |
|---|---|---|
| `actor_eliminated(victim_actor_id, killer_actor_id, weapon_icon)` | validated bullet/melee/elimination paths | `round_manager.gd` (stats) |
| `actor_disarmed(victim_actor_id, disarmer_actor_id, weapon_icon)` | validated disarm paths | `round_manager.gd` (stats) |
| `actor_gun_picked_up(actor_id)` | `gun.gd` | `round_manager.gd` (stats) |
| `actor_melee_hit_landed(actor_id)` | `melee_weapon.gd` | `round_manager.gd` (stats) |
| `actor_combat_feedback(attacker_actor_id, event_kind)` | validated combat paths | `hit_marker.gd` |
| `actor_damage_direction(victim_actor_id, source_world_direction, source_kind)` | valid local bullet contacts / host-authored online hit relay | `damage_direction_indicator.gd` in the victim's viewport HUD |
| `player_eliminated(...)`, `player_disarmed(...)`, `gun_picked_up(...)` | gameplay presentation paths | kill feed / match HUD only |
| `gun_dropped()` | `gun.gd` | `match_hud.gd` (notification) |
| `hud_notification(message)` | `round_manager.gd` and other systems as needed | `match_hud.gd` |
| `combat_noise(world_position, source_actor_id, kind, loudness)` | footsteps/weapons/items | bot perception |

This bus is the primary decoupling mechanism in the codebase: gameplay scripts never hold direct references to UI or the round manager, they only emit signals and let interested systems subscribe.

## 9. UI Architecture

UI is composed of small, single-responsibility scripts, each polling or listening to one thing and rendering it, rather than one large HUD controller:

- `match_hud.gd` — round/set banner, remaining-player drama states, notification toasts (via `hud_notification`), and the TAB-driven `UI/arena_matchboard.gd`. The Arena Matchboard is a lightweight live overlay: official/custom status, mode/map/round/timer context, compact round-score pips, kills/disarms, alive state, local/host/One Gun markers, and team grouping. It renders at most six competitor rows: the true top five plus the viewer's actual row when they place 6th–10th, or the true top six when the viewer is already top five or has no actor. Detailed secondary stats remain available to the post-match results flow.
- `gun_ui.gd` / `melee_ui.gd` / `reload_spinner.gd` — weapon/item status. The spinner renders both gun reload and grenade-cook progress with no numbers.
- `inventory_slots.gd` — the three-slot (weapon, item1, item2) display, including a per-slot `HoldBar` (`ProgressBar`) that fills while that slot's `interact_hold_active`/`interact_hold_timer` hold-to-drop is in progress (see §6).
- `item_ui.gd` — shows whichever item slot is currently active (mirrors how `gun_ui.gd`/`melee_ui.gd` only show while the weapon slot is active), not both items at once.
- `stamina_bar.gd` / `dash_charges.gd` / `powerup_status.gd` — player-resource displays, each reading directly off the local player controller.
- `throw_arc_overlay.gd` / `flash_camera_overlay.gd` / `flash_blind_overlay.gd` — viewport-scoped aiming/flash presentation. Keeping all three inside each HUD is essential in splitscreen: one player's arc, camera frame, or blindness must never spill into the other half.
- `crosshair.gd` / `UI/crosshair_renderer.gd` — one procedural renderer shared by local and online HUDs. It may visualize movement, firing, normalized `gun.get_reload_progress()`, and a camera-ray-validated nearby interactable, but never writes aim/spread/accuracy/network state.
- `hit_marker.gd` — a non-stacking typed combat-feedback renderer. Validated elimination feedback takes precedence over an active ordinary hit; gun, melee, and optional hazard event kinds can select distinct presentation without coupling combat code to the HUD.
- `damage_direction_indicator.gd` — a procedural COD-style red incoming-fire arc. Each local HUD filters the victim-keyed event by actor ID, rotates the stored world-space impact bearing against that player's camera, merges near-duplicate hits, caps simultaneous arcs, and preserves a lethal bearing across the immediate spectator rebind. Online sends one reliable, round-epoch-guarded event per valid bullet contact; no UI state is continuously synchronized.
- `UI/accessibility_manager.gd` — the focused accessibility adapter. It applies UI/text scale, contrast, color filters and optional screen motion blur globally; player/bot/theme code queries it for shake, bob, reduced-motion, and flash policy.
- `kill_feed.gd`, `status_label.gd`, `round_label.gd` — presentation-only, driven by either direct player state or `GameEvents`.
- `player_ui_container.gd` — the per-viewport root that composes the local HUD. After its owner is eliminated it rebinds every `set_player()` child read-only to the current follow target, and restores the owner when spectating ends.

- `UI/winners_circle.gd` — an opaque full-screen match-end layer with native-resolution UI and one isolated 960×540 3D SubViewport for the top-three podium, character copies, Victory Moves, ceremonial gun, trophy drop, and quality-scaled confetti/lights. Its SubViewport texture temporarily fills the screen for the ceremony without duplicating the 3D world. Character visuals begin hidden; their selected move or fallback idle is loaded, played and advanced before the root fades in, and a visual with no valid animation remains hidden rather than exposing its bind pose. All fourteen shipped animated products resolve through one unified local dance library. The independent `emote` and `round_victory_move` loadout columns choose where a dance appears, so any owned dance may run on the podium, after a round win, or in both places; animated dances loop cleanly for either presentation. `UI/winners_circle_stage_blockout.gd` owns the deterministic third-place pullback, second-place swish, champion Catmull-Rom orbit, placement spotlight changes and final Trophy/confetti beat. `audio/ui/winners_circle_ceremony.wav` is the free Ceremony March default; the approved B/C/D/E/F/H alternates live under `audio/ui/winners_circle_themes/`. `SupabaseCosmeticRegistry` maps owned `ceremony_theme` IDs to those fixed local audio keys, the sanitized ID travels in the normal cosmetic roster/result snapshot, and every peer plays the champion's equipped theme with a safe default fallback. The results column remains transparent and mouse-blocked beneath the cinematic, then appears through a brief black transition after the hero shot. It renders shared standings, full stats, per-local-player results, and return controls without reusing gameplay actors, physics, cameras, or network synchronizers. `GraphicsQualityManager` automatically applies the selected render scale and effects density to this SubViewport and its nodes; Reduced Motion replaces dances with idle, uses a static wide camera, skips confetti, and makes the Trophy transition immediate.
  The ceremony set is now authored as the modular `UI/winners_circle_stage_blockout.tscn`: three separately replaceable, shared-origin Blender exports provide the static shell, podiums, and decor, while `UI/winners_circle_stage_blockout.gd` attaches live characters, equipped cosmetics, Trophy, confetti, and dynamic nameplates to validated Godot anchors. The generation, replacement, and performance contract lives in `docs/design/WINNERS_CIRCLE_BLOCKOUT.md`.

## 10. Splitscreen & Spectating

- `player.tscn` gives each gameplay camera a layer-1 `SpringArm3D`, so map geometry retracts the camera while players/items remain transparent to the collision query. The non-ADS view preserves the authored 4.0m boom and configured FOV while `character_body_3d.gd` applies a distance-compensated right/up shoulder offset; ADS interpolates into its approved closer shoulder offset as the boom and FOV tighten. The offsets differ in world space so the mascot retains a stable lower-left screen composition at both distances. This keeps every shipped Hat out of the non-ADS center sight lane without camera-relative cosmetic hiding. `character_body_3d.gd` rejects mouse-look input whenever `PauseManager` owns a pause overlay.

- `splitscreen_manager.gd` maintains two `SubViewport`s (P1 left, P2 right), copying each player's camera transform into the corresponding viewport's `Camera3D` every frame. When `GameConfig.split_screen_enabled` is false, P2's viewport is hidden, its renderer is disabled, and P1's stretches full width. ## 12. Online Multiplayer

- `NetworkManager` is a transport-neutral session layer backed by ENet/UDP. Tailscale remains an optional listen-host discovery/addressing path, not a requirement of ENet itself. It owns host/join, compatibility negotiation, peer roster/names/roles, authoritative `GameConfig`/map sync, monotonically increasing match and human actor IDs, coordinated scene changes, and match-scene readiness. The build/protocol payload is independent of ENet so a future transport can reuse the same admission contract.
- `build_info.gd` separates player-facing `GAME_VERSION`, compatibility-gating `NETWORK_PROTOCOL`, and artifact `build_id`. Local unstamped runs use `dev`; `tools/stamp_build.ps1` generates ignored `build_metadata.json` with a channel/commit ID before export. Both export presets include that file. Servers log their build and each admitted client build, lobby metadata carries the server build, and the main-menu footer displays the local build. ## 13. Data-Driven Patterns Worth Preserving

- **Input prefix pattern**: all gameplay input reads go through `input_prefix + "_action"` — new player-specific actions must follow this convention, receive both P1/P2 controller defaults where relevant, and be included in device filtering/routing or splitscreen will silently break for one player. Shared UI controls such as `pause` and `scoreboard` deliberately remain unprefixed.
- **Interactable registration**: pickup objects register themselves into the player's `nearby_interactables` array rather than the player scanning the tree — new pickup types should follow this registration pattern to stay consistent with gun/melee/item pickup.
- **`pick_up()` returns success/failure, not void**: since §6's rework, every pickup-able object's `pick_up()` returns `true`/`false` so the caller can tell whether anything happened — required for the player's tap-vs-hold decision. Any new pickup type must follow this contract.
- **Shared collision and timing, data-driven identity**: all melee types use the same scene-owned capsule and Frying Pan phase timing, while `WeaponData` retains stamina, visual, and grip data. Adding a weapon means adding one `_build_x()` function without authoring another gameplay hitbox.
- **GameConfig as single source of truth for rules**: UI (lobby toggles), gameplay (round manager, weapons), and persistence (presets) all read/write the same autoload fields — avoid shadowing these values locally in gameplay scripts.
